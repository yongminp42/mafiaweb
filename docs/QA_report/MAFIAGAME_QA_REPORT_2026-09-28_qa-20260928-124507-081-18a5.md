## 13. 원인 분석

RoomPresenceService.currentState는 빈 방이 DB 삭제를 기다리는 동안 로비에 0명 상태를 유지한다. 두 실패 테스트는 비동기 삭제 완료를 기다리지 않은 직후 null을 기대했다. 테스트의 room-cleanup 지연이 Duration.ZERO여도 삭제 작업은 maintenance worker에서 비동기로 실행된다.

cancelsGameDepartureWhenThePlayerReconnectsWithinTheGracePeriod는 테스트 이름과 달리 첫 join 전에 방 상태를 PLAYING으로 준비하지 않았다. WAITING 방에 마지막 세션이 떠나면 room cleanup 예약이 생기므로, 재접속이 게임 탈주 유예를 검증하지 못하고 삭제 중인 방으로 거부됐다.

ongoingGameAllowsRejoinButRejectsNewParticipantWithoutChangingPresence는 먼저 WAITING 방에 join해 RoomPresenceService의 roomStatusByRoom 캐시를 만든 뒤 Mockito DB 응답만 PLAYING으로 바꿨다. 실제 game start는 서비스를 통해 이 캐시도 전환하므로, 테스트는 실제 상태 전환 대신 오래된 상태를 주입했다.

두 Playwright 오류는 사용자 화면의 XP가 없어서가 아니라, XP 총량과 “다음 레벨까지” 숫자를 같이 포함하는 strong 범용 locator가 strict mode에서 여러 요소를 선택해 생겼다. 사용자 프로필 템플릿의 XP 본문 값은 화면에 존재했으며 locator가 그 요소 하나를 좁혀 선택하지 못했다.

docs/MAFIAGAME_MVP.md에는 서로 다른 역할표가 중복되어 있다. 앞선 표는 5인에 Spy가 있다고 적지만 후속 표 및 실행된 RoomGameServiceTest는 5인에 CITIZEN 2명, Spy는 6인부터라고 검증한다. 같은 문서의 이전 phase 설명은 10/60/15/15/15/30초이고 실행된 서비스 테스트와 QA runbook은 15/60/20/20/20/35초다. 이번 Smoke의 runtime 실패는 아니지만 기준 문서 정리가 필요하다.

## 16. 권고하는 수정

1. XP locator를 XP 요약 행 안의 strong 하나만 선택하도록 좁힌다. 예: article의 .d-flex > strong.
2. 빈 방 제거 테스트는 RoomPresenceService의 pending-cleanup snapshot이 null로 바뀔 때까지 제한 시간 안에서 대기한다. 삭제 호출만 검증하지 말고 삭제 완료 이후의 상태를 검사한다.
3. 게임 재접속 테스트는 첫 join 전부터 PLAYING 상태를 제공한다. WAITING room cleanup과 game departure grace를 한 테스트에서 혼합하지 않는다.
4. 프로필 role table과 phase duration을 docs/MAFIAGAME_MVP.md에 하나의 기준으로 정리한다.
5. QA 실행 하네스는 Playwright 명령 전에 $env:E2E_RUN_ID=$e2eRunId를 동일한 PowerShell 프로세스에서 설정하고, core/UI에 같은 ID를 전달한다.
6. 현재 최적화 관련 Java/mapper/controller/JavaScript 테스트 결과는 통과했지만 성능 benchmark 숫자는 이번 실행에서 재측정하지 않았다.
