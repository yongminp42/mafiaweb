# MAFIAGAME 발표 구성안과 대본

> 최종 발표본: [단일 HTML 발표자료](./MAFIAGAME_PRESENTATION.html). 표지 포함 19장(본문 01~18), 슬라이드별 안내 시간 합계 10분 기준. 발표 대본은 이 문서에서만 관리하며 HTML 슬라이드 아래에는 표시하지 않음.

## 변경사항 반영 검토

- HTML의 표지 포함 19장과 본문 01~18 순서에 맞춰 대본을 정렬하고, 슬라이드에 표시된 정보·도식·코드 흐름을 발표자가 별도로 보충하지 않아도 설명할 수 있도록 대본을 확장함.
- 로그인·회원가입·홈페이지 로비·게임 시작 전 대기실의 실제 화면 4종을 UI 정의서 한 장에 2×2로 배치하고 대본을 통합함. 게임방 대기실을 인게임 화면으로 잘못 소개하지 않도록 반영함.
- 기술 스택의 역할, WebSocket 대안과 선택 이유, Flyway의 마이그레이션 역할, 클래스·ERD·시퀀스 도식의 읽는 법을 구체화함.
- 트러블슈팅과 버그 리포트는 발생 조건, 원인, 처리 순서, 확인된 수치와 측정 범위를 포함함. 측정하지 않은 장애 건수·복구 시간은 성과 수치로 만들지 않음.
- 최적화 그래프와 코드 설명에 측정 조건, 전후 수치, 메시지 전달 범위, 남아 있는 목록 p95 회귀를 포함함. 개선 전후 그래프의 순번이 동일 요청을 짝지은 비교가 아님을 명시함.
- 마지막 대본은 ‘감사합니다’로 마무리함. 안내 시간 합계는 10분임.

## 슬라이드별 대본

### 표지 · MAFIAGAME (20초)

**발표 대본**

안녕하세요. MAFIAGAME 프로젝트를 발표하겠습니다. 네 명에서 여덟 명이 한 방에 모여 역할을 받고 토론과 투표로 승패를 겨루는 웹 마피아 게임입니다. 프로젝트 배경과 기술, 주요 화면과 구조, 장애 대응, 실제 적용한 최적화와 핵심 코드 흐름을 차례로 설명하겠습니다. 각 장은 핵심 화면과 코드 근거를 연결해 보여드리며, 결과 수치는 측정 조건과 함께 설명하겠습니다. 게임 규칙 판정을 서버에 모아 참가자별 화면이 서로 다른 상태로 움직이지 않게 하는 것도 중요한 목표였습니다.

### 01. 배경과 요구사항 (35초)

**발표 대본**

WebSocket을 채팅뿐 아니라 게임 흐름 전반에 활용하고 싶어 이 프로젝트를 시작했습니다. 입장과 준비, 역할 배정, 투표와 밤 행동이 여러 사용자에게 맞게 전달되어야 합니다. 요구사항에는 방장 권한, 4~8명 정원, 전원 준비 확인, 단계별 행동 검증을 두었습니다. 서버가 공개 정보와 개인 역할을 구분해 전달하며 재접속 동기화와 결과 후 재대기까지 처리하는 것을 목표로 했습니다. 한 화면의 상태만 보여주는 데 그치지 않고, 참가자가 같은 진행 단계에 있는지 계속 맞추는 것이 핵심이었습니다.

### 02. 현재 프로젝트 기술 스택 (30초)

**발표 대본**

요청 흐름에 따라 기술을 소개합니다. 브라우저 화면은 HTML, CSS, JavaScript, Bootstrap 5.3.8과 Thymeleaf로 구성합니다. Java 17, Spring Boot 3.5.16에서 Spring MVC가 웹 요청을 받고 Spring Security가 인증을 담당합니다. 실시간 통신은 Spring WebSocket과 브라우저 WebSocket API이며, 프로젝트의 STOMP 프레임 클라이언트가 목적지를 구분합니다. MyBatis로 MariaDB에 접근하고 Gradle로 관리합니다. Flyway는 버전 SQL과 적용 이력을 관리하며 V2에서 user_name 고유 제약을 적용합니다. 테스트 전용 의존성은 제외했습니다. 이 구성에서는 HTTP 화면 렌더링과 실시간 메시지 경로가 나뉘며, 데이터베이스 변경은 서버가 담당합니다. Flyway는 적용한 버전의 이력을 남기므로, 실행 환경마다 어떤 데이터베이스 변경이 반영됐는지 추적할 수 있습니다.

### 03. WebSocket과 대안 기술 (25초)

**발표 대본**

대안으로 폴링, Long Polling, SSE, WebRTC 데이터 채널이 있습니다. 폴링은 주기적으로 반복 요청하고 Long Polling은 변경까지 응답을 보류합니다. SSE는 서버에서 브라우저로 보내는 방식이라 행동 제출은 별도 요청이 필요합니다. WebRTC는 피어 연결과 신호 교환을 관리해야 합니다. 서버가 규칙을 판정하고 양방향 메시지를 처리하는 이 게임에는 WebSocket이 맞다고 판단했습니다. 대안보다 항상 빠르다는 의미는 아닙니다. 폴링은 변경이 없어도 요청이 반복되고, SSE와 WebRTC는 단방향 전달과 피어 연결이라는 차이가 있습니다. 각 방식의 연결 유지, 통신 방향과 반복 요청량을 비교해 서버 중심 게임에 필요한 특성을 우선했습니다.

### 04. 기능별 클래스 구조 · 핵심 흐름 (30초)

**발표 대본**

클래스 다이어그램은 로비·참가, 게임, 계정·인증, 채팅으로 기능을 묶었습니다. 상자는 실제 클래스와 대표 멤버이고, 실선 화살표는 필드 참조, 점선은 메서드 의존, 채워진 마름모는 소유 관계입니다. Controller가 요청을 받고 Service가 권한과 상태를 확인해 도메인 처리나 저장 계층을 호출하는 구조를 보여줍니다. 기능별 탭에서 관계를 따라가면 전체 호출 흐름을 볼 수 있습니다. 관계선은 임의로 연결한 것이 아니라 실제 코드의 필드나 호출 관계를 기준으로 설명합니다.

### 05. 전체 선언 타입 · 상세 UML (20초)

**발표 대본**

앞 페이지가 핵심 관계라면 여기는 전체 선언 타입입니다. 소스 51개 파일과 내부 타입 19개, 총 70개를 11개 기능 도식으로 나눴습니다. 클래스 외에 인터페이스, 열거형, 레코드도 포함했습니다. 점선과 열린 삼각형은 인터페이스 구현 관계입니다. 내부 타입도 집계했으므로 70개는 파일 수가 아니라 선언된 타입 수입니다.

### 06. ERD · 실제 자료형과 키 (35초)

**발표 대본**

이 ERD는 클래스가 아닌 SQL 테이블 구조입니다. user는 계정, user_stats는 전적, game_room은 방 설정, room_members는 참가 상태, game_completion은 종료 결과를 저장합니다. user_stats.user_id는 사용자에 대한 PK·FK라 통계 행은 사용자당 최대 하나입니다. room_members는 room_id와 user_id의 복합 PK로 참가를 식별합니다. game_completion.room_id는 DDL에 FK가 없어 관계선이 없습니다. 컬럼 자료형과 PK·FK·UK를 표시했으며 user_name 고유 제약은 Flyway V2와 맞춥니다. 자료형은 각 컬럼의 저장 형태를, 키 표시는 식별과 참조 제약을 보여줍니다. 따라서 테이블 관계와 코드 클래스 관계를 구분해야 합니다. 이름과 이메일의 고유 제약, 방 상태와 정원, 참가자의 준비·역할·생존 값처럼 키 외의 데이터도 함께 표현합니다.

### 07. 게임 시작 왕복 시퀀스 (30초)

**발표 대본**

시퀀스는 위에서 아래로 시간이 흐르고 참여자 사이에 요청과 응답이 오갑니다. 방장의 시작 요청을 Controller와 서비스가 받아 방장 세션, 대기 상태, 참가자 4~8명, 전원 준비를 검증합니다. RoomService가 DB 상태를 바꾸고 성공하면 게임 서비스가 역할을 준비합니다. 공개 페이즈는 방 토픽, 비밀 역할은 사용자별 큐로 보냅니다. 검증 결과와 브로커 전달은 별도 흐름이며 STOMP SEND 자체가 응답을 만들지는 않습니다. 검증 조건이 맞지 않으면 게임을 시작하지 않습니다. 성공 후에는 공개 상태와 비밀 역할이 서로 다른 경로로 전달됩니다. 실선은 요청 호출, 점선은 반환이나 메시지 전달 결과입니다. 시작 검증에 실패하면 게임 초기화 단계로 넘어가지 않습니다.

### 08. UI 정의서 · 주요 화면 4종 (65초)

**발표 대본**

이 페이지는 로그인부터 게임 시작 전 대기실까지 실제 화면 네 장을 2×2로 보여줍니다. 왼쪽 위 로그인에서는 이메일과 비밀번호로 접속하고, 오른쪽 위 회원가입에서는 계정 정보와 약관을 입력해 새 계정을 만듭니다. 왼쪽 아래 홈페이지 로비에서는 접속 인원과 방 목록을 보고, 검색이나 상태 필터로 방을 찾거나 새 방을 만들 수 있습니다. 캡처 당시에는 활성 방이 없어 목록이 비어 있습니다. 방을 선택하면 오른쪽 아래의 게임방 대기실로 이어집니다. 대기실은 인게임 화면이 아니라 시작 전 준비 화면입니다. 참가자와 빈자리, 방 설정, 준비 상태와 대기 채팅을 확인할 수 있습니다. 예시는 네 자리 중 한 명만 입장한 상태입니다. 방장은 참가 인원과 전원 준비 조건이 충족된 뒤 게임을 시작합니다. 네 화면을 통해 신규 사용자의 계정 진입, 방 탐색, 게임 참여 전 준비 흐름을 한 번에 볼 수 있습니다.

### 09. 트러블슈팅 · 시작 실패 뒤 PLAYING 고착 방지 (35초)

**발표 대본**

시작 요청은 방장·대기 상태·참가자 4~8명·전원 준비를 확인한 뒤 DB를 PLAYING으로 바꾸고 게임을 초기화합니다. 이때 역할 배정, 게임 등록, 타이머 예약, 첫 방송에서 예외가 나면 DB와 메모리 상태가 달라질 수 있습니다. 실패 시 생성된 게임과 타이머를 정리하고 WAITING으로 롤백합니다. DB 롤백도 실패하면 메모리를 PLAYING으로 유지하고 두 오류를 기록합니다. 재시작 시 메모리 게임은 없으므로 DB에 남은 PLAYING 방을 WAITING으로 복구합니다. 장애 수나 복구 시간은 측정하지 않았습니다. 이 대응은 재시작 뒤 게임 상태를 되살리는 것이 아니라, 진행 중으로 남은 방을 대기 상태로 돌리는 복구입니다. 첫 방송까지 성공해야 시작 처리가 완료됩니다. 초기화가 실패하면 재시작 없이도 대기실에서 다시 시작할 수 있도록 정리합니다.

### 10. 버그 리포트 · 새 방 인원 이벤트와 전체 새로고침 (30초)

**발표 대본**

버그는 로비에 없는 새 방의 인원 이벤트를 받았을 때 발생했습니다. 기존 코드는 카드가 없으면 150밀리초 뒤 로비 전체를 다시 불렀습니다. 수정 후 방 ID로 해당 카드 HTML만 가져와 추가합니다. 천 개 방 측정에서 이벤트당 HTML 본문은 1,027,013바이트에서 906바이트로 99.91퍼센트 감소했습니다. CSS와 이미지, 전체 서비스 트래픽은 포함하지 않은 수치입니다. 방 카드가 이미 있으면 그 카드를 갱신하고, 없을 때만 새 조각을 요청해 중복 삽입을 막습니다.

### 11. 적용된 최적화 요약 (35초)

**발표 대본**

실제 적용한 변경은 세 가지입니다. 방 목록 참가자 집계를 줄여 동시성 1의 200쿼리 배치 평균을 2.017초에서 0.296초로 낮췄습니다. 준비 변경 p50은 3.6131밀리초에서 1.1050밀리초가 됐습니다. 인원 변화가 없는 준비 변경에서 로비 인원 메시지는 640건에서 0건으로 줄었습니다. 단, 천 개 방 전체 목록 p95는 141.38밀리초에서 171.14밀리초로 늘어 전체 목록까지 개선됐다고 말할 수는 없습니다. 이번 측정만으로 목록 p95 악화 원인을 단정하지 않았습니다. 따라서 쿼리 배치 시간과 준비 변경 지연, 메시지 수는 개선됐지만 전체 목록 지표는 추가 원인 분석이 필요합니다.

### 12. 실측 그래프로 본 최적화 효과 (25초)

**발표 대본**

왼쪽은 쿼리 한 건이 아닌 200개 쿼리 배치 평균입니다. 동시성 1은 2.017초에서 0.296초, 8은 0.453초에서 0.174초로 줄었고 각각 7회 반복했습니다. 오른쪽은 네 클라이언트 준비 변경 40회 결과입니다. p50은 3.6131에서 1.1050밀리초, p95는 6.0234에서 2.0567밀리초로 낮아졌습니다. 이 측정 조건에 한정된 비교입니다. 막대는 공통 시간 눈금으로 길이를 비교하므로, 감소 비율 자체를 막대 높이로 읽지는 않습니다. SQL 조건별 감소율은 동시성 1과 8에서 다르므로 그래프도 두 결과를 분리해 비교합니다.

### 13. 준비 상태 변경 80개 묶음 선 그래프 (25초)

**발표 대본**

위 선 그래프는 네 클라이언트가 동시에 준비 또는 해제한 묶음의 지연, 아래는 누적 평균입니다. 40회 반복, 총 320개 요청에서 지연 표본은 80개였습니다. 아래 평균선은 측정이 쌓일 때 평균이 어떻게 변하는지 보여줍니다. 개선 전후는 별도 실행이므로 같은 순번끼리 동일 요청을 짝지은 값은 아닙니다.

### 14. 메인 메뉴 로직 · 첫 화면과 방 생성 (35초)

**발표 대본**

코드는 로비 표시와 방 생성 흐름입니다. GET /rooms는 RoomService의 방 정보와 RoomPresenceService의 실시간 인원을 RoomView로 결합해 rooms/list에 전달합니다. 온라인 수는 전체 세션 수와 방별 인원 합계 중 큰 값입니다. 생성 요청은 제목·정원·비밀번호 조건을 검사해 방과 방장 참가 정보를 저장합니다. 성공하면 접근 권한을 세션에 주고 이동하며, RoomCreationException이면 오류와 입력값을 폼에 돌려줍니다. 방 이름과 설정은 DB에서, 현재 인원은 세션 상태에서 가져와 하나의 화면 모델에 결합합니다.

### 15. 로비 실시간 로직 · 참가 인원과 새 방 반영 (30초)

**발표 대본**

연결 후 브라우저는 먼저 인원 토픽을 구독하고 스냅샷을 요청합니다. 서버 응답으로 방별 인원과 전체 접속 수를 갱신합니다. 새 방 이벤트가 오면 기존 카드는 인원만 바꾸고 0명이면 제거합니다. 없는 카드는 중복 요청을 막고 HTML 조각을 받아 삽입한 뒤 검색·필터를 갱신합니다. 이 처리로 로비 전체를 새로고침하지 않습니다. 이후 이벤트뿐 아니라 연결 시점의 전체 상태도 받아 로비 숫자를 초기화한다는 점이 흐름의 핵심입니다.

### 16. 게임방 대기실 로직 · 입장·준비·시작 (35초)

**발표 대본**

대기실 입장에는 방 ID, WebSocket 세션, 로그인 사용자와 비밀번호 접근 권한이 전달되고 결과는 해당 사용자 큐로 돌아갑니다. 준비 변경은 방 참가 세션인지, 상태가 WAITING인지 확인한 뒤 방 전체에 알립니다. 시작 시에는 방장, 대기 상태, 참가자 4~8명, 전원 준비를 확인합니다. 모두 통과해야 DB와 메모리 게임을 바꾸며 초기화 실패 시 WAITING 롤백을 시도합니다. 입장 결과는 신청자 개인 큐로, 준비 상태 변경은 방 토픽으로 보내는 점에서 정보 수신 범위가 다릅니다.

### 17. 게임 진행 로직 · 역할 배정과 행동 검증 (40초)

**발표 대본**

게임 서비스는 참가자 스냅샷으로 역할을 배정하고 역할 확인 페이즈와 타이머를 설정합니다. 공개 페이즈·생존 상태는 방 토픽, 개인 역할은 사용자 큐로 전달합니다. 행동 요청은 게임 상태, 기한, 참가자 존재와 생존 여부를 먼저 확인한 뒤 역할 확인·지목 투표·처형 찬반·밤 행동 중 허용된 처리를 선택합니다. 방 잠금 안에서 검증·기록하고 잠금 해제 뒤 방송합니다. 타이머가 끝나면 행동을 정산해 다음 페이즈로 이동합니다. 다른 페이즈의 행동이 들어오면 상태를 바꾸지 않습니다. 상태 방송은 잠금 밖에서 진행해 전파 중 방 상태를 오래 붙잡지 않습니다. 행동을 기록한 뒤에는 최신 상태를 스냅샷으로 만들고, 공개 정보와 개인 정보를 각 수신 범위에 맞게 전달합니다.

### 18. 마무리 (20초)

**발표 대본**

MAFIAGAME은 입장부터 역할 배정, 행동, 결과 확인과 재대기까지 이어지는 실시간 웹 게임입니다. 서버가 규칙을 판정하고 공개 정보와 개인 정보를 나눠 전달합니다. 적용한 최적화와 남아 있는 목록 p95도 구분해 설명드렸습니다. 이상으로 발표를 마치겠습니다. 감사합니다.
