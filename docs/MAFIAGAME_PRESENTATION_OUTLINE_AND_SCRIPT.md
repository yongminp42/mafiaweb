# MAFIAGAME 발표 구성안과 대본

> 최종 발표본: [단일 HTML 발표자료](./MAFIAGAME_PRESENTATION.html). 표지 포함 17장(본문 01~16), 슬라이드별 안내 시간 합계 7분 기준. 발표 대본은 이 문서에서만 관리하며 HTML 슬라이드 아래에는 표시하지 않음.

## 변경사항 반영 검토

- HTML의 표지 포함 17장과 본문 01~16 순서를 유지하면서, 발표 시간 7분에 맞춰 핵심 정보·근거 수치·도식 흐름 중심으로 대본을 압축함.
- 로그인·회원가입·홈페이지 로비·게임 시작 전 대기실의 실제 화면 4종을 UI 정의서 한 장에 2×2로 배치하고 대본을 통합함. 게임방 대기실을 인게임 화면으로 잘못 소개하지 않도록 반영함.
- 01번 요구사항 슬라이드를 현행 명세의 회원·방·실시간 게임·채팅·재접속·결과 기능군으로 재구성함. 기술 스택, WebSocket 대안, Flyway와 도식의 핵심 설명을 유지함.
- 트러블슈팅과 버그 리포트는 발생 조건, 원인, 처리 순서, 확인된 수치와 측정 범위를 포함함. 측정하지 않은 장애 건수·복구 시간은 성과 수치로 만들지 않음.
- 중복되는 실측 최적화 그래프와 전체 선언 타입 UML 슬라이드를 삭제하고, 남은 슬라이드 번호와 대본을 다시 정렬함. 80개 묶음 선 그래프에는 측정 조건과 전후 실행의 비대응 관계를 설명함.
- 마지막 대본은 ‘감사합니다’로 마무리함. 안내 시간 합계는 7분임.

## 슬라이드별 대본

### 표지 · MAFIAGAME (10초)

**발표 대본**

안녕하세요. 제가 만든 웹 마피아 게임, MAFIAGAME을 소개하겠습니다. 4명에서 8명까지 한 방에서 실시간으로 플레이하는 프로젝트입니다.

### 01. 배경과 요구사항 (28초)

**발표 대본**

이 프로젝트는 WebSocket을 게임 전반에 써보고 싶어서 시작했습니다. 여러 사람이 같은 방에서 동시에 움직이려면, 준비 상태나 투표 결과가 바로 공유돼야 하니까요. 그래서 회원과 방 관리부터 역할, 투표, 밤 행동, 채팅, 재접속, 결과 기록까지 하나의 흐름으로 만들었습니다. 게임은 방장이 시작하고, 4~8명이 모두 준비해야 합니다.

### 02. 현재 프로젝트 기술 스택 (30초)

**발표 대본**

화면은 HTML·CSS·JavaScript, Bootstrap과 Thymeleaf로 만들었습니다. 서버는 Java 17과 Spring Boot, 인증은 Security가 맡습니다. WebSocket·STOMP로 실시간 메시지를 주고받고 MyBatis·MariaDB에 저장합니다. Flyway는 DB 변경을 순서대로 적용하며, V2에서 user_name 중복을 막았습니다.

### 03. WebSocket과 대안 기술 (27초)

**발표 대본**

WebSocket을 게임에 넓게 써보려는 목표가 있었습니다. 준비·투표·행동은 서버로 보내고, 판정 결과는 다시 받아야 합니다. 공개 정보는 방 전체에, 역할은 본인에게만 전달하죠. WebSocket과 STOMP는 한 연결에서 양방향 통신을 하고, 받을 대상을 구분합니다. 그래서 이 게임 구조에 맞았습니다.

### 04. 기능별 클래스 구조 · 핵심 흐름 (24초)

**발표 대본**

이 그림은 클래스 이름보다 요청이 지나가는 길을 보시면 됩니다. 로비에서 방에 들어오거나 게임 행동을 보내면, 컨트롤러가 요청을 받고 서비스가 참가 상태와 규칙을 확인합니다. 처리한 결과는 화면이나 방 전체, 또는 해당 사용자에게 돌아갑니다. 아래 화살표에 네 기능의 흐름을 짧게 정리했습니다.

### 05. ERD · 실제 자료형과 키 (28초)

**발표 대본**

ERD는 데이터가 어디에 연결되는지 보시면 됩니다. 사용자가 방을 만들거나 참여하면 사용자와 방이 연결되고, 참가 이력은 room_members에 쌓입니다. 통계는 user_stats에 이어집니다. 자료형과 키는 실제 SQL 기준입니다. room_members는 두 ID가 복합 키이고, game_completion의 room_id에는 외래 키가 없습니다.

### 06. 게임 시작 왕복 시퀀스 (22초)

**발표 대본**

이번에는 요청이 돌아오는 과정까지 보겠습니다. 방장이 시작을 누르면 서버는 방장 권한, 대기 상태, 인원과 준비 여부를 확인합니다. 조건이 맞으면 방 상태를 바꾸고 게임을 초기화하죠. 그다음 공개 상태는 방 전체에, 비밀인 역할 정보는 각자의 개인 채널에 보내서 브라우저에 다시 표시합니다.

### 07. UI 정의서 · 주요 화면 4종 (29초)

**발표 대본**

실제 화면은 로그인, 회원가입, 로비, 게임방 대기실 순서입니다. 로그인한 뒤 로비에서 접속 인원과 방 목록을 보고, 검색이나 필터로 원하는 방을 찾거나 새 방을 만들 수 있습니다. 이 캡처에서는 아직 활성 방이 없었습니다. 오른쪽 아래는 게임 중 화면이 아니라 시작 전 대기실이고, 네 자리 가운데 한 명이 들어온 상태입니다.

### 08. 트러블슈팅 · 시작 실패 뒤 PLAYING 고착 방지 (31초)

**발표 대본**

게임을 시작할 때 발견한 문제입니다. 시작 조건을 통과해 DB 상태를 PLAYING으로 바꾼 뒤, 역할 배정이나 타이머 예약에서 실패하면 방만 게임 중으로 남을 수 있었습니다. 그래서 실패한 게임과 타이머를 정리하고 방 상태를 WAITING으로 되돌리게 했습니다. 서버 재시작 때도 실제 게임이 없는 PLAYING 방을 복구합니다. 이 부분은 장애 건수나 복구 시간을 따로 측정한 결과는 아닙니다.

### 09. 버그 리포트 · 새 방 인원 이벤트와 전체 새로고침 (28초)

**발표 대본**

로비에 없는 새 방에서 인원 이벤트가 오면, 예전에는 방 목록을 통째로 다시 받았습니다. 이제는 방 ID로 그 카드만 받아 추가하고, 기존 카드는 갱신합니다. 천 개 방 조건에서 이벤트 HTML 크기가 1,027,013바이트에서 906바이트로, 99.91% 줄었습니다. 전체 트래픽이 아니라 해당 응답의 크기입니다.

### 10. 적용된 최적화 요약 (31초)

**발표 대본**

실제로 적용한 최적화 결과입니다. 방 목록 SQL의 배치 평균은 동시성 1에서 2.017초에서 0.296초로, 동시성 8에서는 0.453초에서 0.174초로 줄었습니다. 준비 변경 지연의 중간값도 3.6131밀리초에서 1.1050밀리초로 낮아졌습니다. 인원 변화가 없을 때 보내던 로비 메시지는 640건에서 0건이 됐고요. 다만 천 개 방의 전체 목록 p95는 오히려 늘었습니다. 이 부분은 남은 과제입니다.

### 11. 준비 상태 변경 80개 묶음 선 그래프 (22초)

**발표 대본**

이 그래프는 준비 상태를 바꾸는 요청을 시간 순서대로 본 겁니다. 위 선은 80개씩 묶은 지연이고, 아래 선은 그때까지의 누적 평균입니다. 네 명이 준비와 해제를 반복해 총 320건을 보냈습니다. 변경 전과 후는 각각 따로 실행했기 때문에 같은 위치의 점을 같은 요청으로 보시면 안 됩니다.

### 12. 메인 메뉴 로직 · 첫 화면과 방 생성 (22초)

**발표 대본**

코드 흐름도 화면에서 시작해 보겠습니다. 로비를 열면 서버가 저장된 방 목록과 현재 접속 인원을 가져와 합친 뒤 화면에 보여줍니다. 새 방을 만들 때는 제목, 정원, 비밀번호를 확인하고 방과 방장 정보를 저장합니다. 입력에 문제가 있으면 생성 화면으로 돌아가 오류를 보여줍니다.

### 13. 로비 실시간 로직 · 참가 인원과 새 방 반영 (22초)

**발표 대본**

로비가 열린 뒤에는 브라우저가 인원 변경 메시지를 구독합니다. 메시지가 오면 전체 인원과 각 방의 인원 표시를 바꿉니다. 이미 보이는 방은 카드만 고치고, 새 방이면 서버에서 그 카드 하나를 받아 넣습니다. 그래서 목록 전체를 새로고침하지 않고도 현재 검색과 필터를 유지할 수 있습니다.

### 14. 게임방 대기실 로직 · 입장·준비·시작 (22초)

**발표 대본**

방에 들어갈 때 서버는 입장 가능 여부를 확인하고, 결과를 그 사용자에게 돌려줍니다. 준비 상태가 바뀌면 참가자이고 대기 중인 방인지 확인한 뒤 방 전체에 알립니다. 시작 요청에서는 방장, 4~8명, 전원 준비를 다시 확인합니다.

### 15. 게임 진행 로직 · 역할 배정과 행동 검증 (30초)

**발표 대본**

게임이 시작되면 서버가 역할을 배정하고 페이즈 시간을 잡습니다. 모두가 알아야 할 상태는 방에 보내지만, 역할은 각자에게만 보냅니다. 누군가 행동을 제출하면 지금 할 수 있는 행동인지, 시간이 지났는지, 살아 있는지와 역할이 맞는지 확인합니다. 유효한 행동을 기록한 다음 결과를 전파하고, 시간이 끝나면 그 페이즈를 정산해 다음 단계로 넘어갑니다.

### 16. 마무리 (14초)

**발표 대본**

정리하면, 이 프로젝트는 방 입장부터 게임 결과까지 서버가 규칙을 판정하고 상태를 실시간으로 나눕니다. 개선된 점과 남은 목록 지연도 함께 살펴봤습니다. 들어주셔서 감사합니다.

## 발표 전 확인

- 표지의 발표자 항목은 실제 발표자명으로 교체.
- HTML은 표지 포함 17장임. 본문 번호는 01~16이며, 코드 페이지는 12~15페이지임. 대본은 7분 기준으로 이 문서에서 관리함.
- 최적화 결과는 2026-09-28 성능 비교 자료의 측정 조건에 한정됨. /rooms 전체 페이지 p95는 개선되지 않았음.
- 슬라이드별 안내 시간 합계는 7분임. 각 대본에는 슬라이드의 도식·수치·코드 흐름을 말로 설명할 문장을 포함함. 실제 발표에서는 그림을 가리키거나 화면 전환하는 시간에 따라 리허설 후 속도를 조정.
