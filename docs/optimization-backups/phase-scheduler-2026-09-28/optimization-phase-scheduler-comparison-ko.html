MAFIAGAME · PERFORMANCE REPORT · 2026-09-28

페이즈 스케줄러 최적화
전후 성능 비교

모든 게임방의 페이즈 종료 콜백을 작업자 한 명이 차례대로 처리하던 구조를 네 명이 처리하도록 바꿨습니다. 같은 시각에 여러 방의 콜백이 만료되는 부하를 재현해, 방 수가 늘어날 때 대기시간이 어떻게 달라지는지 측정했습니다.

현재 소스 상태: 이 보고서의 4개 작업자 구현은 비교 실험 당시의 임시 변경이며, 요청에 따라 롤백되어 현재 기본 작업자는 1개입니다. 아래 수치는 당시 실험의 기록으로 보존한 결과이며 현재 실행 코드의 성능을 나타내지 않습니다. 백업 및 재적용 안내를 확인하세요.

01 · 결과 요약

방이 겹쳐 만료될 때, 대기열 지연이 줄었다

콜백 자체의 일을 줄인 실험이 아니라, 서로 다른 방이 같은 작업자 한 명을 기다리는 시간을 비교했습니다. 작업자 네 명을 쓰면 한 번에 최대 네 방의 콜백을 시작할 수 있어, 여러 방이 동시에 만료되는 조건에서 p95 대기시간이 낮아졌습니다.

소스코드의 핵심 변경

기본 생성자가 작업자 수 네 개를 선택하도록 하고, 같은 스케줄러 구현을 작업자 수 1개로 실행하는 생성자도 두었습니다. 이 생성자는 전후 실험과 단위 검증에서 동일한 코드 경로를 비교하는 데 사용했습니다.

// 이전 기본값
Executors.newScheduledThreadPool(1, threadFactory);

// 변경 후 기본값
private static final int DEFAULT_WORKER_COUNT = 4;

GamePhaseScheduler() {
    this(DEFAULT_WORKER_COUNT);
}

GamePhaseScheduler(int workerCount) {
    // 스레드 이름은 room-game-phase-1, room-game-phase-2 ...
    this.executor = Executors.newScheduledThreadPool(workerCount, threadFactory);
}

작업자 수만 늘리면 같은 방의 타이머 교체 경합에서 이미 시작된 콜백이 새 예약을 지울 수 있습니다. 이를 막기 위해 예약마다 식별자를 붙였습니다. 예약이 현재 방의 최신 식별자인지 실행 전에 확인하고, 콜백이 방 잠금을 얻은 뒤에도 자기 식별자가 여전히 유효한지 확인합니다.

// 방별 예약 작업의 식별자를 콜백에 전달
phaseScheduler.schedule(roomId, delay, taskId -> advancePhase(game, taskId));

// 방 잠금 안에서 현재 예약과 일치할 때만 페이즈 변경
if (!phaseScheduler.complete(game.roomId, scheduledTaskId)) {
    return; // 취소·교체된 오래된 콜백
}

실험 당시 전체 구현은 GamePhaseScheduler 스냅샷과 RoomGameService 변경 패치에서 확인할 수 있습니다.

03 · 측정 방법

동일한 콜백 부하를 1개와 4개 작업자에 각각 적용

측정 대상실제 GamePhaseScheduler의 예약·실행 경로. 이전 조건은 작업자 1개, 변경 후 조건은 기본 작업자 4개.
동시 방 수1, 2, 4, 8, 16개. 각 방의 콜백을 같은 250ms 지연으로 예약했습니다.
콜백 본문각 콜백이 시작한 뒤 고정 50ms 대기. 실제 측정 처리시간 p50은 Windows 실행환경에서 약 62ms였습니다.
반복과 표본각 작업자 수·방 수 조합을 7회 반복했습니다. 총 434개 콜백 표본입니다. 두 작업자 조건의 실행 순서는 반복마다 교차했습니다.
대기 지연실제 콜백 시작 시각에서 예약된 만료 시각을 뺀 시간입니다. 예약 호출 시간과 운영체제의 타이머 깨우기 오차가 일부 포함됩니다.
처리시간콜백 진입부터 고정 대기 종료까지입니다. 콜백 처리 로직 자체가 빨라지는지 확인하기 위한 보조 지표입니다.
환경Windows 11, Java 21.0.12, 사용 가능한 프로세서 24개. 측정일 2026-09-28.

측정의 범위: 게임방과 실제 DB·WebSocket을 연결한 운영 부하 측정은 아닙니다. 실제 스케줄러에 일정한 처리시간의 콜백을 넣어 작업자 대기열 효과를 분리했습니다. 따라서 아래 수치는 이 재현 조건에서 확인한 값이며, 실제 게임 페이즈 지연이 같은 비율로 줄어든다고 보장하지 않습니다.

05 · 같은 방 안전성

방 사이의 병렬 처리와 방 안의 순서 보장을 분리했다

방마다 기존 잠금을 그대로 사용

RoomGameService.advancePhase()는 해당 GameRoom의 game.lock을 얻은 뒤 페이즈 상태를 변경합니다. 각 게임방은 별도 잠금을 사용하므로, 방 A의 전환이 방 B의 전환을 막지 않으면서도 한 방의 상태는 한 번에 한 작업만 변경합니다.

기존 게임 인스턴스 확인도 잠금 획득 전후에 수행합니다. 새 게임이 같은 방 ID를 사용하면 이전 게임 콜백은 현재 게임이 아님을 확인하고 반환합니다.

예약 식별자로 취소·교체된 콜백 걸러내기

같은 방의 타이머를 교체해도 이미 실행을 시작한 이전 콜백은 즉시 멈추지 않을 수 있습니다. 작업자 네 개 구조에서는 이 경합이 더 쉽게 겹칠 수 있어 예약별 식별자를 비교하게 했습니다.

테스트에서 실행 중인 구 예약이 신 예약을 완료 처리하지 않는지, 같은 방 예약 교체와 명시적 취소가 동작하는지, 서로 다른 방 4개가 실제로 함께 시작하는지 확인했습니다.

06 · 결과를 읽을 때 주의할 점

대기열 병목은 줄었지만, 운영 지연 전체를 측정한 결과는 아니다

이 실험으로 말할 수 있는 것

  • 콜백 처리시간이 약 62ms일 때, 동시 만료된 방 콜백을 네 작업자로 나누면 방 사이 대기시간이 감소했습니다.
  • 16개 방에서 대기 p95는 941.283ms에서 202.353ms로 738.930ms 줄었습니다.
  • 콜백 처리 p50은 1개와 4개 작업자에서 거의 같았습니다. 개선된 부분은 콜백 내부 처리시간이 아니라 작업자 앞의 대기입니다.

아직 측정하지 않은 것

  • 실제 방의 게임 진행, DB 통계 저장, WebSocket 전송을 포함한 end-to-end 페이즈 전환 지연
  • 동시 콜백 네 개가 DB·메시지 브로커·CPU 사용량에 주는 영향
  • 4개를 초과하는 작업자 수, 실제 운영에서 동시 만료되는 방의 분포, 장시간 지속 부하
  • 사용자 화면에서 타이머 0초 이후 실제 전환까지 걸리는 시간

해석: 한 방만 만료된 조건에서는 작업자 네 개의 우위가 거의 없습니다. 이 최적화의 효과는 여러 방의 만료 시각이 겹치는 상황에 한정됩니다. 실제 페이즈 처리 안에서 DB 저장이나 브로드캐스트가 오래 걸리면 그 처리시간 자체는 그대로이며, 작업자 네 개가 동시에 그런 일을 할 때 생기는 외부 자원 경합은 이번 실험에 포함되지 않았습니다.

후속 운영 확인 항목

  • 여러 게임방의 종료 시각이 겹칠 때 예약 만료 시각과 실제 페이즈 변경 시각을 함께 기록합니다.
  • 방별 콜백 대기시간과 처리시간을 분리해 p50·p95·최댓값을 관찰합니다.
  • 같은 방에서 페이즈가 중복 또는 역순으로 바뀌지 않는지 확인합니다.
  • 실제 부하에서 DB 응답시간, 메시지 전송 대기, CPU와 스레드 수를 함께 봅니다.
