# 최적화 대상: 페이즈 콜백 단일 작업자 병목

> 이 파일은 2026-09-28 최적화 실험 당시의 문서 사본이다. 최적화 소스는 이후 롤백되어 현재 기본 작업자는 한 개다. 다시 적용할 때는 같은 폴더의 [백업 및 재적용 안내](README.md)를 참고한다.

## 확인된 구조

최적화 전 `GamePhaseScheduler`는 `Executors.newScheduledThreadPool(1, ...)`로 작업자 한 명을 만들었다. 이 스케줄러 인스턴스는 `RoomGameService`가 관리하며, 각 게임방의 페이즈 종료 콜백을 모두 여기에 예약했다. 현재 기본 작업자 수는 네 개다.

따라서 서로 다른 방의 페이즈 종료 시각이 겹치면 한 콜백이 실행되는 동안 나머지 콜백은 같은 작업자 대기열에서 기다린다. 한 방의 콜백이 늦어지면 그 시각에 만료된 다른 방도 늦게 처리될 수 있다.

관련 코드:

- `src/main/java/kr/or/oti/mafiagame/service/GamePhaseScheduler.java`: 작업자 네 개로 예약 작업 실행, 방별 작업 식별자 관리
- `src/main/java/kr/or/oti/mafiagame/service/RoomGameService.java`: 방별 잠금 안에서 현재 예약 콜백만 페이즈 전환

## 지연 계산 예시

동시에 만료된 콜백이 `K`개일 때, 마지막 콜백의 추가 대기시간은 앞에서 실행되는 콜백들의 실행시간 합에 가까워진다.

```text
마지막 콜백의 추가 대기시간 ≈ 앞선 콜백 실행시간의 합
```

| 동시에 만료된 콜백 | 콜백당 가정 실행시간 | 마지막 콜백의 예상 추가 대기 |
| ---: | ---: | ---: |
| 5개 | 50ms | 약 200ms |
| 10개 | 200ms | 약 1.8초 |

위 숫자는 동작 구조를 설명하기 위한 계산 예시다. 현재 실행환경에서 콜백 시간과 동시 만료 방 수를 측정한 값은 아니다.

## 수정 범위

개선 대상은 **모든 방의 페이즈 콜백을 작업자 한 명이 직렬 처리하는 구조**였다. 기본 작업자를 네 개로 늘려 서로 다른 방의 콜백을 병렬 실행할 수 있게 했다. 같은 방 안의 상태 전환은 기존 `game.lock`으로 순서를 보장하며, 예약 작업 식별자로 교체되거나 취소된 구 콜백이 최신 예약을 완료 처리하지 못하게 했다. 다른 게임 규칙, 페이즈별 대기시간, DB 통계 저장, 브라우저 카운트다운은 이 최적화 범위에 포함하지 않는다.

개선 시 서로 다른 방의 콜백은 병렬 실행할 수 있게 하되, 같은 방 안의 상태 전환은 기존 `game.lock`으로 순서를 보장해야 한다. 타이머 취소와 이전 게임 콜백 방지 동작도 유지한다.

## 검증 기준

여러 방의 만료 시각을 겹치게 해 개선 전후를 비교했다. 핵심 지표는 다음 두 값이다.

- 콜백 대기 지연: 예약 만료 시각부터 실제 콜백 시작까지
- 콜백 처리시간: 콜백 시작부터 종료까지

동시 방 수별 p50·p95·최댓값을 비교했다. 예약 교체·취소, 실행 중인 구 예약 식별, 서로 다른 방의 병렬 실행을 단위 테스트로 확인했다.

## 측정 상태

- Java 21.0.12, Windows 11에서 실제 `GamePhaseScheduler`에 고정 50ms 대기 콜백을 넣어 작업자 1개와 4개를 비교했다. 동시 방 1·2·4·8·16개 조건을 각각 7회 반복해 434개 콜백을 측정했다.
- 16개 방의 대기 p95는 941.283ms에서 202.353ms로 78.50% 감소했다. 4개 방에서는 202.836ms에서 15.311ms로 92.45% 감소했다. 콜백 처리 p50은 약 62ms로 비슷했다.
- 실제 게임·DB·WebSocket 경로의 운영 지연은 이 실험에서 측정하지 않았다. 상세 측정 조건, 전체 방 수별 원자료, 그래프와 한계는 [전후 성능 비교 보고서](optimization-phase-scheduler-comparison-ko.html)를 참고한다.
