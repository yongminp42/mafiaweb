01 · 큰 그림

병목은 “한 번의 큰 작업”보다 반복되는 작은 작업에 있었다

준비 버튼과 방 목록은 자주 실행됩니다. 각각의 처리에서 DB 조회, 집계, 메시지, 페이지 전송이 불필요하게 반복되면 사용자 수가 늘수록 부담도 커집니다.

개선 전

상태를 보낼 때마다 DB 확인

방 상태 스냅샷을 만들면서 DB를 읽고, 그동안 공용 쓰기 잠금이 유지됐습니다.

개선 후

이미 메모리에 있는 방 설정과 상태로 스냅샷을 만듭니다.

개선 전

목록마다 참가 인원 재집계

SQL이 참가 테이블을 합치고 방별로 세었습니다.

개선 후

목록 SQL은 방 기본 정보만 읽고, 화면에 실시간 인원을 합칩니다.

개선 전

변화가 없어도 재전송

준비 상태만 바뀌어도 로비 인원 메시지가 갔고, 새 방에는 전체 페이지를 다시 받았습니다.

개선 후

인원 변화가 있을 때만 메시지를 보내고, 새 방은 카드 하나만 받습니다.

02 · 실시간 상태

준비 버튼을 누를 때 DB 대기와 잠금 대기를 줄였다

방의 현재 인원, 잠금 여부, 게임 상태처럼 자주 쓰는 값은 RoomPresenceService가 이미 관리합니다. 이번 변경은 상태 스냅샷에서 방 DB를 다시 읽는 과정을 없앴습니다.

이전 흐름

준비 상태 변경→공용 쓰기 잠금→스냅샷용 DB 조회→방 상태 전파

현재 흐름

준비 상태 변경→메모리 설정·상태 조회→방 상태 전파

소스코드는 이렇게 달라졌다

핵심 흐름을 쉽게 표현한 의사코드입니다.

이전 snapshot(roomId)
  → requireRoom(roomId)
  → roomService.getRoom(roomId)  // DB

현재 snapshot(roomId)
  → roomSettingsByRoom.get(roomId)
  → roomStatusByRoom.get(roomId)  // 메모리

방 입장의 DB 조회와 빈 방 삭제의 DB 작업도 공용 쓰기 잠금 밖으로 옮겼습니다.

잠금 밖에서 읽어도 안전한 이유

방 입장은 먼저 DB 정보를 읽고, 잠금을 얻은 뒤 roomDeletionGeneration과 삭제 진행 상태를 다시 확인합니다. 그 사이 방 삭제가 시작됐다면 오래된 조회 결과를 그대로 쓰지 않고 다시 시도합니다.

즉, DB를 기다리는 동안 다른 사용자의 상태 변경을 막지 않으면서 삭제와 입장의 경쟁도 확인합니다.

03 · 방 목록 SQL

이미 가진 참가 인원을 DB에서 또 세지 않는다

기존 목록 쿼리는 room_members를 합친 뒤 방마다 COUNT와 GROUP BY를 수행했습니다. 현재 인원은 실시간 서비스가 알고 있으므로, 조회 결과 위에 그 값을 얹도록 했습니다.

이전 SQL 개념
game_room + room_members
  → 방마다 GROUP BY
  → COUNT(참가자)
  → 목록 반환

방 수와 참가 기록이 많아질수록 집계 작업도 반복됩니다.

현재 SQL 개념
game_room + 방장 정보
  → 기본 목록 반환
  → 실시간 인원으로 덮어쓰기

findAll과 findById에서 참가 테이블 집계를 제거했습니다.

04 · 로비 메시지

준비 상태가 바뀌어도 인원수가 같으면 다시 알리지 않는다

방 안의 준비 상태 메시지는 계속 필요합니다. 그러나 준비 버튼만 누른 경우 참가 인원과 온라인 인원은 그대로입니다. broadcast 경로에서 이전에 보낸 인원과 현재 인원을 비교하도록 바꿨습니다.

준비 상태 변경→방 내부 상태 전송 유지+인원 변화 없으면 로비 전송 생략

입장·퇴장처럼 실제 인원이 바뀌면 로비 갱신은 계속 갑니다. 이 수치는 인원이 변하지 않는 준비 상태 부하에서의 억제 효과입니다.

05 · 새 방 표시

새 방이 생겼을 때 목록 전체 대신 카드 하나만 받는다

이전 room-list.js는 새 방을 발견하면 잠시 뒤 /rooms 전체 페이지를 다시 열었습니다. 이제 GET /rooms/{roomId}/card에서 실제 Thymeleaf 카드 HTML 한 개를 받고 목록에 넣습니다.

→
▣새 카드 한 장만 받기개선 후 · 906B · 방 1개

새 방 1건 이벤트의 HTML 전송 크기 99.91% 감소 · 약 1/1,134 수준

상자는 개념도이며 면적 비율이 아닙니다. 수치는 실제 응답 본문 크기입니다. 전체 서비스 트래픽이 99.91% 감소했다는 뜻은 아닙니다.

브라우저에서 바뀐 흐름

  1. 로비 이벤트가 아직 목록에 없는 방을 알립니다.
  2. loadRoomCard()가 카드 경로를 요청합니다.
  3. 받은 카드를 기존 목록에 삽입합니다.
  4. 검색·필터·목록 번호를 다시 맞춥니다.

06 · 함께 바뀐 구조

작업 대기열과 중복 검증도 정리했다

예약 작업을 분리

기존에는 로비 인원수 전송과 빈 방 삭제, 방장 이전, 게임 이탈 처리가 작업자 1개의 대기열을 공유했습니다. 이제 유지보수 작업자는 2개이고, 로비 인원수 예약 전송은 전용 작업자 1개가 맡습니다.

서로 다른 작업이 같은 한 줄 대기열에서 기다릴 가능성을 줄인 구조 변경입니다. 겹치는 유지보수 부하의 개선 시간은 별도로 측정하지 않았습니다.

방 설정 검증을 한곳으로

RoomService의 방 생성과 설정 변경에 반복되던 최대 인원·비밀번호 정규화 및 길이 검증을 공통 함수로 모았습니다. 같은 규칙을 한곳에서 고칠 수 있어 분기 차이가 생길 위험을 줄입니다.

기존 입력 규칙과 오류 문구를 유지했습니다. 이 변경의 독립적인 속도 개선치는 측정하지 않았습니다.

07 · 측정값을 읽는 법

SQL이 빨라져도 전체 페이지가 항상 빨라진 것은 아니다

/rooms는 여전히 방 1,000개 카드를 한 번에 HTML로 만듭니다. DB 집계를 줄였어도 렌더링과 전송 비용이 남아 있습니다. 실제 전체 페이지 측정은 지표에 따라 좋아지거나 나빠졌습니다.

측정 조건과 검증 범위

2026-09-28, 별도 MariaDB 스키마에 방 1,000개와 참가 기록 4,000개를 넣고 비교했습니다. SQL은 200쿼리 배치를 7회, HTTP는 10회 예열 + 30회 측정, STOMP는 40회 반복 × 준비/해제 2묶음 × 4명으로 측정했습니다.

변경 당시 Java 컴파일과 리소스 처리, JavaScript 테스트 41건이 통과했습니다. 실제 Spring/Thymeleaf 페이지의 방 1,000개 렌더링과 카드 응답도 확인했습니다. 수치별 원자료는 이 파일과 같은 폴더에 보관되어 있습니다.
